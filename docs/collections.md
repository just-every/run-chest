# Finish collecting the right records

A file request's upload receipt says that bytes were admitted. It does not say
that the material is current, approved, or received by the intended colleague.

Create a folder with version review, then a file request with a checklist, such
as **Signed supplier agreement** and **Tax record**. From **Collection checklists**,
the installation owner selects requested records, names the intended active
staff recipients and chooses whether reminders stay as drafts or may be sent at
an approved cadence. Recipients must already have access; a checklist grants none.

For each requirement, select the exact submitted item and version. Chest compares
its request/checklist identity, submission outcome, latest/current version, exact
human approval and each recipient's current download access. A stale replacement
or an admitted-but-unapproved upload remains a mismatch. Selecting a submission
never approves it. The owner sees matching candidates and the reasons evidence
still needs attention.

The intended recipient opens the checklist and explicitly confirms the exact
approved version. A file view, a byte transfer and a mail-provider acknowledgment
cannot make that confirmation. Matching transfer events appear separately as
supporting evidence. Once every record is current, approved and personally
confirmed by every intended recipient, the checklist is accepted and reminders
stop.

Later replacements, changed approval or recipient access reopen the mismatch and
invalidate old confirmations. The page proposes reviewing the new delivery;
it never adds recipients, grants access or approves a replacement. Restored access
requires fresh confirmation. Owners can pause the checklist or turn automatic
reminders off. Reminder drafts and actual provider outcomes remain visible.

Only the checklist owner and intended recipients can inspect it, subject to live
folder and file access. Recipients see their own confirmation and delivery history.
Automatic reminders run on hosted Chest's existing fifteen-minute schedule and
on application traffic, rechecking the standing owner authority, recipient access
and approved cadence before sending. A failed or suppressed send remains visible;
it is not converted into a successful receipt or replayed as a queued send.
